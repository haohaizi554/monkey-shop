# MonkeyShop 全站 UI 与交互体验设计规格

日期：2026-07-12

状态：已自审，待用户书面复核

方案：A - 消费者商城与工业级后台双模式统一壳

## 1. 背景与现状

MonkeyShop 当前包含消费者商城、账户与履约流程，以及商品、库存、营销、风控、数据和租户管理页面。前端基于 Vue 3、Vue Router、Pinia 和 Element Plus。

现有工作区已经进行过一轮大范围 UI 修改，但验收证据表明仍有系统性问题：

- 19 个路由页面分别实例化 `AppShell`，全局 chrome 的所有权仍落在页面层。
- 消费者页面与后台页面共用同一条顶部导航，信息架构没有区分浏览购物与高频运营。
- 品牌入口与商城导航使用相同可访问名称，造成自动化严格定位冲突。
- `useNotify`、`useAsyncState` 和 `AppErrorBoundary` 已出现，但只在少量页面使用或尚未接入。
- 页面仍存在大量直接 `ElMessage` 调用、布尔加载状态、原始色值和局部样式。
- 登录主视觉依赖后端静态资源；后端不可用时会出现破图和大块空白。
- 当前 lint、可访问性和全路由 smoke 尚未全部通过，且 smoke 首个异常缺少路由上下文。

本规格不把局部美化视为完成。完成必须同时覆盖架构所有权、视觉系统、状态反馈、组件行为、响应式、可访问性、性能和浏览器证据。

## 2. 目标

1. 建立消费者与后台双模式、同品牌、不同密度的统一应用壳。
2. 让全部路由共享稳定的设计 Token、组件状态和反馈语言。
3. 消除重复导航、页面级全局 chrome、卡片堆叠和视觉漂移。
4. 统一 loading、updating、success、empty、error、disabled 状态及恢复路径。
5. 将错误放在用户可恢复的位置，减少干扰性 Toast，并彻底隐藏原始后端文案。
6. 提升表格、筛选、表单、弹层、导航和移动端操作的效率与可访问性。
7. 通过 lint、构建、可访问性、全路由 smoke、截图和控制台检查证明完成。

## 3. 非目标

- 不替换 Vue、Element Plus、Pinia 或现有 API 层。
- 不修改后端业务规则，除非前端需要已有错误元数据或静态资源契约。
- 不创建营销落地页，也不添加与现有业务无关的页面或虚构数据。
- 不为追求视觉新奇重写所有 Element Plus 组件。
- 不把桌面 PyQt/PySide 规则强行套入当前 Web 项目。

## 4. 用户与使用场景

### 4.1 消费者

消费者以浏览、搜索、比较、购买、支付、履约、评价和账户管理为主。界面需要友好、图片清晰、动作明确，并在手机上保持 44px 以上触控目标。

### 4.2 运营与管理员

管理员以扫描、筛选、比较、批量判断和重复操作为主。界面需要紧凑、克制、可预测，优先使用表格、工具栏、状态标签和内联反馈，而不是装饰性卡片。

## 5. 信息架构与应用壳

### 5.1 路由所有权

- `App.vue` 只负责根配置、错误边界和路由出口。
- 路由布局层拥有全局壳；页面组件只拥有场景内容。
- 路由 `meta.area` 明确为 `consumer`、`admin` 或 `auth`。
- 所有页面移除自身的 `AppShell` 包裹，避免页面层重复创建全局 chrome。

### 5.2 消费者壳

桌面端采用单行品牌导航：品牌、商城/搜索主入口、购物车、账户、语言和主题。管理员登录时提供明确的“进入管理后台”入口，但不把全部后台导航塞进消费者导航。

移动端保留紧凑顶部栏，并为商城、搜索、购物车、订单和我的提供稳定底部导航。底部导航只在消费者与账户路由显示，不覆盖结算主动作。

### 5.3 后台壳

桌面端采用固定左侧导航和顶部工作区栏：

- 商品运营：商品、库存、营销。
- 运营治理：数据、风控、租户。
- 顶部栏只保留当前页面标题、面包屑、全局状态和账户动作。
- 内容区使用明确的最大宽度、最小轨道和滚动所有权。

窄屏下左侧导航折叠为抽屉，顶部保留菜单、标题和核心动作。表格横向滚动发生在表格容器内，不让整页横向溢出。

### 5.4 登录壳

登录、注册、重置密码共用独立认证布局：真实 MonkeyShop 图片作为宽屏主视觉，表单保持在同一视口内；移动端优先表单并将图片收缩为短幅品牌区域。主视觉资源必须打包到前端或提供本地可靠回退，不依赖后端在线才能显示。

## 6. 视觉系统

### 6.1 定位

- 叙事角色：消费者端是可信、清晰的自然主题商城；后台是安静、高密度的运营工具。
- 观看距离：手机 10-30cm、桌面 50-80cm。
- 视觉温度：消费者端温暖但不幼稚；后台权威、克制、工作导向。
- 容量：消费者页面留出图片与商品比较节奏；后台优先容纳表格和工具栏。

### 6.2 设计决策

- Anchor：自定义“自然主题商业 + 工业级运营”，不套用通用 SaaS 模板。
- 主色：Forest `#176B4D`，用于主要动作、选中和品牌识别。
- 强调色：Canopy Gold `#B7791F`，用于价格、商业提醒和少量重点。
- 信息色：Clear Blue `#2563A6`，只用于信息状态和链接。
- 中性色：Ink `#172033`、Muted `#667085`、Line `#D8DEE8`、Canvas `#F4F6F8`、Surface `#FFFFFF`。
- 成功色：`#067647`；危险色：`#B42318`；警告色：`#B54708`。三者使用独立语义 Token。
- 深色主题：Graphite 中性底色配森林绿和金色强调，不使用整页深蓝/藏青单色主题。
- 字体：打包 Noto Sans SC 可变字体；正文、标题、数字都使用明确字重，数字启用 tabular-nums。
- 间距：4px 基线，核心序列为 4/8/12/16/20/24/32/40/48/64。
- 圆角：控件 6px、卡片和弹层 8px；胶囊仅用于标签，圆形仅用于头像或图标按钮。
- 阴影：页面区块无阴影；重复商品卡使用轻微层级；弹层和对话框使用单独高层阴影。
- 动效：快速反馈 140ms，结构变化 220ms，统一 easing；遵守 `prefers-reduced-motion`。

所有 CSS 值通过语义 Token 消费。页面级样式不得新增原始十六进制颜色、私有圆角体系或独立动效时长。

## 7. 组件与页面表面

### 7.1 公共组件

- `AppShell`：路由区域解析、消费者/后台 chrome 和响应式导航。
- `PageHeader`：标题、说明、面包屑和页面主动作。
- `PageToolbar`：搜索、筛选、排序、刷新和批量动作。
- `AsyncState`：骨架、空态、错误和重试表面。
- `FeedbackHost`：分组 Toast、全局事件和可选 trace 信息。
- `StatusTag`：稳定的业务状态到视觉语义映射。
- `DataTableShell`：表格滚动、空态、分页、密度和移动降级。
- `FormSection`：表单分组、内联校验、提交状态和脏数据保护。
- `ConfirmAction`：危险操作确认，不在页面中散落不同 MessageBox 配置。

公共组件保持行为与视觉分离：行为组件维护 open、focus、disabled、pending 等状态；视觉只消费 Token。

### 7.2 页面表面规则

- 页面章节不做浮动卡片；使用无框分区、分隔线或背景带。
- 卡片只用于商品、订单等重复实体，以及确实需要边界的工具或弹层。
- 按钮使用 Lucide/Element Plus 图标；熟悉的动作优先图标并提供 tooltip/aria-label。
- 弹层必须支持 Escape、外部点击策略、焦点圈、焦点返回和移动端宽度。
- 表单在字段旁显示验证与恢复信息，提交失败不清空有效输入。

## 8. 状态机与异步数据

统一资源状态：

`idle -> loading -> success | empty | error`

已有有效数据时刷新使用 `updating`，保留旧内容并在局部显示刷新状态。提交动作使用独立 `pending` 状态，不复用页面 loading。

`useAsyncState` 必须满足：

- 每次请求有序号或 AbortController，旧请求不能覆盖新请求。
- timeout 后到达的结果不能把 error 静默改回 success。
- loading 必须有成功、空、错误、超时和取消退出路径。
- error 保留可恢复上下文和用户可读文案。
- updating 默认保留上一次有效数据。

后台轮询与高频事件遵循：页面不可见时暂停主体刷新；进度事件采用 latest-state-wins；表格按稳定 ID 更新，禁止因单行变化重置全表。

## 9. 通知、错误与确认

### 9.1 反馈层级

1. 字段错误：显示在字段旁。
2. 页面/区块加载错误：显示在失败区块内，提供重试。
3. 业务阻断：显示可操作的 Alert，解释权限、登录、密码更新或限流恢复方式。
4. Toast：只用于成功、轻量信息或跨页面完成事件。
5. 对话框：只用于不可逆或高影响确认。

### 9.2 错误规范

- 禁止直接显示 `Too many requests`、`Operation is not permitted` 等原始后端文案。
- 401 引导登录；403 解释权限或密码更新；429 说明等待时间并抑制重复请求。
- 可诊断错误保留 trace ID，但放在可展开详情或复制动作中，不抢占主文案。
- 同类消息分组、去重并限制同时显示数量。
- 登录页错误留在表单内部，不作为全局顶部大通知。

## 10. 消费者页面设计

- 商城：首页直接是可用商品目录，工具栏支持搜索、价格和库存筛选；商品图片、名称、价格和库存形成清晰优先级。
- 搜索：查询、筛选、排序和分页同步到 URL；返回页面保持状态。
- 商品详情：图片与购买面板并列，移动端改为单列；主动作稳定，不因加载文案改变尺寸。
- 购物车：选择、数量、价格和结算动作可扫描；移动端使用条目列表和固定结算栏。
- 结算/支付：步骤和金额摘要清晰；重复提交受保护，失败保留选择和地址。
- 订单/物流/评价：以时间、状态和下一动作组织，不显示内部枚举。
- 会员/资料：把高频任务分组，敏感信息默认掩码，危险操作远离主要动作。
- 登录：默认登录表单最短路径；注册和重置密码不把所有字段同时堆进首屏。

## 11. 后台页面设计

- 商品管理：工具栏 + 商品表格 + 编辑抽屉/对话框；删除、上下架、图片上传均有行级状态。
- 库存：查询条件持久化；库存、锁定、在途和安全线使用稳定列与状态语义。
- 营销：券、价格试算、秒杀和拼团按任务分区，避免多个平级表单挤在一屏。
- 风控：评估和人工复核分开；风险分、信号、状态和处置动作形成强扫描顺序。
- 数据看板：紧凑指标、漏斗表和画像区；页面隐藏时暂停轮询，手动刷新不覆盖旧数据。
- 租户：租户列表与详情保持 master-detail；配置、账单、导出在详情标签页中，创建租户使用独立表单面板。

筛选、分页和排序在适用页面写入 URL 或持久状态。Mutation 必须有成功、失败和必要的回滚反馈。

## 12. 响应式与可访问性

- 验收视口：390x844、768x1024、1440x900，另检查 320px 最小宽度。
- 页面不得出现整体横向滚动；表格可在自身容器中滚动。
- 手机触控目标至少 44x44px，桌面图标按钮至少 36x36px。
- 所有图像有准确 alt；装饰图像使用空 alt 或 `aria-hidden`。
- 同一页面的可访问名称必须唯一且符合语义。
- 键盘可完成导航、菜单、标签、弹层、表单和确认流程。
- focus-visible 清晰；深浅主题均满足 WCAG AA 对比度。
- 文本允许合理换行，不通过视口宽度缩放字号，不使用负字距。

## 13. 性能与稳定性

- 路由继续懒加载，避免把后台页面打进消费者首屏。
- 图片使用稳定尺寸、懒加载和本地回退，避免布局跳动和后端停机破图。
- 搜索输入防抖；轮询在不可见页面暂停；高频事件合并。
- 大表优先分页，必要时虚拟化；行更新按稳定 ID patch。
- 不在 UI 线程执行阻塞 IO，不在每个进度事件重新拉取全量快照。

## 14. 验收与测试

### 14.1 静态门槛

- `npm run lint`：0 error、0 warning。
- `npm run build`：成功；自有代码不产生新警告。
- 扫描页面与组件：不得新增未映射原始颜色、重复半径系统或直接 `ElMessage` 调用。

### 14.2 状态与组件测试

- `useAsyncState` 覆盖 success、empty、error、timeout、cancel、race、updating。
- 通知覆盖分组、去重、最大数量、错误映射和 trace 详情。
- 弹层覆盖键盘、焦点返回、Escape、外部点击和移动宽度。
- destructive mutation 覆盖确认、pending、失败和恢复。

### 14.3 浏览器门槛

- 19 条业务路由在桌面和移动端全部通过 smoke。
- smoke 在每条路由开始、成功和失败时输出路由及视口，不允许首错丢上下文。
- 全部目标页面控制台 0 error、0 warning，请求 0 unexpected failure。
- Axe WCAG A/AA 无 serious/critical violation。
- 代表性消费者、认证和后台路由在三类视口保存截图并人工复核。
- 登录主视觉、商品图和空态图像进行像素非空检查。
- 深色主题、语言切换、缩放、减少动效和键盘流程通过。

## 15. 实施顺序

1. 质量基线：修复 lint/a11y/smoke 诊断，建立可靠红绿反馈。
2. 视觉基础：Token、字体、Element Plus 桥接、主题和全局表面。
3. 壳与导航：路由布局所有权、消费者壳、后台壳、认证壳。
4. 状态与反馈：错误边界、异步状态机、通知、确认和恢复路径。
5. 消费者流程：商城、搜索、详情、购物车、结算、订单、支付、物流、会员、资料、评价。
6. 后台流程：商品、库存、营销、风控、看板、租户。
7. 性能与验收：轮询、事件合并、全路由检查、截图、Axe、Lighthouse 和最终 CR。

每一阶段必须先通过本阶段测试再进入下一阶段。不得用最后一次集中修 CSS 替代逐页面状态和交互验证。

## 16. 完成定义

只有以下条件全部有当前证据时才可声明目标完成：

- 所有明确页面均已迁移到双模式壳并通过目标视口检查。
- 设计 Token、状态机、通知和组件行为在全站实际使用，而非仅创建未接入的 helper。
- 消费者核心交易流程和后台高频工作流均可从浏览器完整操作。
- lint、build、Axe、全路由 smoke、截图和控制台检查全部通过。
- 不存在已知 P0/P1 UI 阻断、破图、原始后端错误、卡死、页面级横向溢出或不可恢复 loading。
- 当前工作区证据与本规格逐条对应，不能用单一构建成功替代全量验收。
